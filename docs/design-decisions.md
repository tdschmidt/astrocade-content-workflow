# Design decisions and rationale

Updated 2026-10-07. This record preserves decisions, their reasons and superseded proposals. **D54 and the current [PLAN.md](../PLAN.md) take precedence:** the core branch discovers games, learns/plays/captures them, and edits shorts through a CLI; account creation and publication are manual. Earlier workbench/Instagram decisions describe the broader historical scope. The [acceptance record](acceptance.md) tracks current live results and remaining proof.

## Requirements and user choices

| ID | Decision | Reason and consequence |
| --- | --- | --- |

| D02 | Address casual gamers and trend-driven viewers. | Selection can consider both understandable gameplay and supported cultural relevance. |

## Engineering decisions supported by research

These are selected implementation defaults, subject to the explicit feasibility tests in the plan. They are not claims that the user personally selected every technical parameter.

| ID | Decision | Reason and consequence |
| --- | --- | --- |
| D16 | React/Vite, Express, TypeScript, Zod, Playwright, FFmpeg, local JSON records, and local media. | A small coherent stack for the agreed workbench and automation. No database or agent framework is necessary. |
| D17 | Use configurable Google model functions and Tavily Search. | Reuse one provider for visual reasoning, writing, speech, and transcription; use explicit sourced search for the requested research feature. Test account quotas instead of promising unlimited free use. See [editorial research](research-editorial.md). |
| D21 | Select a game-format-payoff concept and analyze recorded moments before final scripting. | Screenshots and popularity alone cannot establish an achievable event. Every gameplay claim needs evidence. |
| D22 | Try timestamped transcription and phrase captions before a native forced-alignment package. | Reduces setup and dependency burden. Recognized text and timing require validation; transcription is not forced alignment. A local Whisper media-tool path is the first alternative to investigate on measured failure. |
| D23 | Prove account creation, live gameplay, recording quality, model capacity, and browser upload before UI expansion. | This replaces the old API-ingestion gate. These are functional dependencies rather than added production NFRs. |
| D24 | Use finalized media timestamps for editing, with coarse analysis followed by denser event windows. | Browser wall-clock observations and sparse video sampling are insufficient cut boundaries. |
| D26 | Use bounded Tavily Search and selective Extract rather than its Research product. | Retains the user-requested capability with predictable credit consumption. Record the difference between directly inspected examples and search metadata. |
| D32 | Give Instagram a dedicated persistent browser profile, separate from gameplay contexts. Start Instagram headed but automate ordinary steps. | A visible browser supports the accepted human handoff. Headed mode is not a claim of avoiding platform detection. Persisted authentication is a secret and stays outside the handoff. |
| D33 | Make the local server the sole workflow writer, with one active mutation operation. | Account setup, generation, rerender, and publishing share one lane. A mutating CLI, if retained, calls that server rather than creating another writer. Freeze edits to an active target until cancellation or completion. |
| D34 | Save publish intent before Share, bind approval to the exact revision/account/caption, and reconcile uncertain outcomes. | Browser publishing lacks the old API container handle. A timeout may occur after success; do not automatically click Share again. |
| D35 | Finalize the edit after measuring actual speech duration. | If speech exceeds authentic footage, shorten and regenerate once. Do not silently repeat a payoff, freeze a long frame, or truncate narration. |
| D36 | Export 1080 by 1920 at 30 fps for the browser upload route. | Current Instagram Help specifies at least 30 fps and 720 pixels. The previously cited Graph API range is no longer the governing path. A higher export rate does not recover missing source frames. See [Instagram research](research-instagram.md). |
| D37 | Use pinned full Chrome/Chromium in unified headless mode for gameplay, with a verified headed fallback. | Local tests proved native input and hardware-backed WebGL on this Mac; actual Astrocade parity remains a separate test. Do not add GPU flags or fake clocks without evidence. See [gameplay research](research-gameplay.md). |
| D38 | Record the composed game tab through native tab capture and explicit VP9 MediaRecorder in a separate local recorder tab. | Local comparative measurements favored its detail and data volume over the built-in recorder and JPEG transport. Matching Playwright 1.63.0/Chromium 153 confirmed 180 distinct frames in six seconds and final-chunk flush. Real-game compatibility remains a gate; JPEG to FFmpeg is a replacement decision if that gate fails, not a second shipped backend. See [capture research](research-capture.md). |
| D39 | Launch a dedicated browser per capture attempt, with its unique capture-title token allocated before launch. | Tab auto-selection is a browser launch argument and cannot be changed by opening a new context. Each attempt owns both game and recorder tabs, releases inputs, flushes recording, and closes its browser. One capture runs at a time. |
| D40 | Park human checkpoints and release the global operation slot after automated work stops. | An identity check should not prevent unrelated video generation. Preserve the Instagram session, reacquire the slot on Resume, and re-observe the page. Keep identity-specific signup and unresolved publication safeguards in force while parked. |
| D41 | Try Mail.tm programmatic provisioning; provide TLS IMAP as the configured alternative. | User requested this change. Persist credentials before creating one identity. Pending creation can authenticate that same identity, but never silently creates replacement addresses. The live attempt could not be verified; IMAP remains available. |
| D42 | Wait for the user's router repair instead of adding VPN Gate. | The user identified the local block and is fixing it. A VPN adds a separate operational dependency without proving better gameplay or Instagram acceptance; unaffected implementation continues. |
| D43 | Expose credential setup in the local workbench, with optional nonempty environment overrides. | The user has no external services configured. Private settings keep setup usable without putting credentials in chat or source; public status only exposes configured flags. |
| D44 | Reuse existing libraries for browser control, media, mail parsing, validation and UI. | User explicitly allows libraries; custom code is limited to the workflow's decisions and integration boundaries. Exact versions and the lockfile support reproducibility. |
| D45 | Preserve publication uncertainty across draft revisions. | Review found that approving a later revision could otherwise bypass an earlier uncertain Share. Block edits/new revision publication until the original intent is reconciled; expose the original recovery action in the UI. |
| D46 | Keep narrated duration content-led and preserve edited words on resume. | A hard twenty-second minimum was unnecessary. Measured speech must fit verified action. Only original generated copy receives one automatic shortening attempt; user-edited revisions require explicit edits. |
| D47 | Check real SDK request serialization with offline fixtures, then require separate live acceptance. | Typed inputs alone do not prove correct media delivery. Tests caught the need to request inline WAV explicitly and use the current nested word-timestamp configuration. They do not establish key access or quota. |
| D49 | Verify timed capture profiles with two independent recordings; analyze content during video generation. | A real gameplay recording succeeded while its subsequent model analysis timed out. Capture readiness should not depend on duplicate model calls. Verification establishes a repeatable, decodable recording, not a claim that every recording contains a good short. |
| D50 | Use the displayed game geometry for native input and recording crops. | Live Astrocade scales its game iframe. Layout bounds caused incorrect coordinates, and automatic scrolling on Start cropped the HUD. Composing frame transforms and checking native click targets preserves the displayed game. |
| D51 | Use low model reasoning for routine analysis and scripting. | A minimal live request took 74 seconds with the default setting and 23 seconds with low reasoning. This reduces unnecessary latency; it does not resolve the separate live footage-analysis timeout or justify unbounded retries. |
| D52 | Ship the tested Crowd Pier Run profile and default to one highlight. | Two fresh live captures and the Studio's two-capture check passed after fixing the loading-overlay race. A new checkout should not require writing JSON to use this proven game. Add missing presets on startup, preserving any saved edits; analyze each recording before making content claims. |
| D53 | Disable hidden model retries and bound Files API requests. | Offline SDK transport tests showed automatic retries continuing after an aborted request, and Files.upload ignoring its supplied abort signal. Use supported SDK timeouts and one attempt; preserve local artifacts for an explicit retry. Upload cancellation may wait for the current bounded HTTP request. No custom uploader is added. |

## Superseded proposals

| Previous proposal | Why it changed | What remains useful |
| --- | --- | --- |
| Owner creates the Instagram account before running the application | The user explicitly rejected externalizing fresh account creation. | Accurate recovery details and exceptional identity checks may still require the owner. |
| Official Instagram Login publishing through a new Meta app | It introduced Facebook/developer prerequisites the user does not have and has ruled out for v1. | It remains background comparison evidence, not a fallback the implementer should quietly build. |
| D18 signed public video URLs and Meta ingestion hosting | Browser publishing uploads the local MP4 directly. D48 also removes shared hosting from delivery scope. | The existing backend local-access boundary stays in place; no sharing setup is needed for the core workflow. |
| D25 API container IDs and `is_ai_generated` request fields | These belong to the removed API publisher. | Exact-revision approval and appropriate disclosure remain; the actual browser controls must be inspected. |
| A generic CLI directly executing alongside the web server | It would violate the single-writer assumption and create avoidable races. | A diagnostic CLI or thin client of the server is compatible. |
| Fixed 25 fps final export based on recorder or API behavior | Browser/Reels Help calls for a 30 fps minimum. | Source cadence must still be measured honestly. |
| Native alignment package as an assumed default | Current provider transcription and existing media-tool alternatives can be simpler. | Add a different timing implementation only after a representative quality or quota failure. |
| Playwright built-in video as the final capture master | Synthetic testing revealed avoidable compression loss and fixed 25 fps. Native VP9 capture performed better in the tested scene. | The built-in recorder remains useful for diagnostics; the research retains a tested JPEG alternative. |

## Historical workbench constraints

Instagram's terms restrict automated account creation and automated access without its permission. The browser route is technically plausible and user-selected; it is not an officially supported provisioning API. Human code entry does not eliminate that platform restriction. Preserve this limitation in the handoff rather than claiming guaranteed unattended creation. [Instagram terms](https://help.instagram.com/581066165581870/)

These integration concerns belonged to the earlier workbench scope. They are not current core-pipeline blockers. Read the [acceptance record](acceptance.md) for current results; the [requirements audit](requirements-audit.md) preserves the earlier planning critique.

## Core-workflow clarification and implementation decisions

| ID | Decision | Reason and consequence |

| D54 | User clarification: deliver only game discovery, learning/play/capture and short-video editing. Keep future publishing discussion brief and hand over finished media/copy. |
| D55 | Run the core directly as a CLI with isolated per-run files and a same-run lock. | The new pipeline owns its own artifacts and does not mutate the workbench workspace, so it needs no HTTP server. | D56 | Nominate up to three games by default, record testable hook/control hypotheses, and choose the final game from actual footage. | Live counters lacked reliable metric labels, making popularity-based ranking unsupported. ### Live-feedback boundary and options for reflex play

The shipped reel loop is **screenshot → model decision → native action batch with timestamped observation frames → one-second settling delay → next screenshot**. The next decision sees a fresh BEFORE frame taken immediately before input, up to six DURING frames, and NOW; the earlier inference-request frame is retained separately. New reel feedback profiles allow up to 600 seconds and 40 decisions by default; the last, if reached, is evaluation-only. Legacy episode defaults remain 175 seconds/16 decisions, and saved profiles retain their recorded limits. Each model call has a deadline of at most 30 seconds; a reel batch permits up to 32 actions after its first probe (legacy: eight), with a declared-duration budget of ten seconds. Confirmed repeatable taps can use a compact native batch of at most 40 clicks over at most six seconds. Individual holds can last six seconds, including two or three observed keys held together. Browser/input overhead can make actual execution longer. The setup prompt assumes decisions may take 5–20 seconds, but that is an eligibility assumption, not a measured latency guarantee. These limits bound work; they do not ensure timely reactions. See [feedback](../src/server/games/feedback.ts), [runner](../src/server/games/runner.ts), and the [live experiments](acceptance.md#gameplay-improvement-experiments-2026-10-06).

The central problem is **observation age when input reaches the game**: capture/encoding, model transport/inference, and input scheduling all add delay. Later actions in a batch use an even older observation. The next opportunity to correct also waits for the batch and settling delay. A faster model or larger decision budget alone does not establish reflex capability. For illustration, a hazard requiring a response within 300ms cannot be handled by a decision arriving seconds later. The one-second settling delay fixed puzzle snapback; a reflex controller would need its own observation cadence rather than applying that delay to moving hazards.

The practical eligibility question is whether **observation age + time for the chosen input to take effect + uncertainty margin fits inside the remaining reaction window**. Also measure the gap between observations: a hazard can appear and become unavoidable while the controller is waiting. These are game-specific feasibility checks, not a new latency requirement from the brief. A deadline merely rejects a late call; it does not guarantee that an accepted decision is still relevant to the current scene.

Car Wash has a countdown and was correctly rejected by this feedback mode. Its successful plan was improved **between attempts**, then executed without model calls during urgent play. Sort It Out tolerates waiting and supports the screenshot loop. Both are useful results, with different control requirements.

| **Faster visual inference with short, interruptible actions** | Games whose reaction window exceeds measured end-to-end latency. A smaller/local model or a lower-latency remote model, cropped observations, and compact outputs could reduce delays. | Unmeasured here. Evaluate capture overhead and slow outliers as well as average inference time. An asynchronous design must use the latest frame, expire stale decisions, and avoid queued actions from obsolete states. Streaming text alone does not establish a usable action sooner. |
| **A policy trained from demonstrations, optionally refined with reinforcement learning** | Repeated use of one game or a stable family justifies learning a fast mapping from recent frames to controls. | Requires representative demonstrations with action timing, a reset/evaluation loop, and training resources; reinforcement learning also needs a useful reward. [VPT](https://arxiv.org/abs/2206.11795) demonstrates imitation learning and subsequent fine-tuning in Minecraft with a native 20Hz mouse/keyboard interface. This supports the approach's plausibility, not transfer to Astrocade. Defer for this take-home unless simpler control fails on a valuable game. |
| **Use a genuine in-game pause or safe checkpoint** | A game with verified pause controls or quiet intervals lets the model inspect the scene and choose the next route or short sequence. | Proposed fallback for obtaining footage, not proof of real-time reflex control. Verify that hazards actually stop during pause. Repeated pauses can interrupt the action; record them honestly and do not present edited footage as uninterrupted play. Do not replace the game's clock or assume browser timers stop every subsystem. |

These approaches can be combined: a model can select a tested skill while a local controller executes and corrects it. [Voyager](https://arxiv.org/abs/2305.16291) provides a precedent for model-guided reusable executable skills in Minecraft. Applying that separation to an Astrocade reflex controller is a design inference, not a result established by that paper or this project. Prefer a few bounded, tested controls over a general skill platform.

For example, in a lane runner the model could learn that coins increase score and barriers end the run, then choose a conservative coin route. A local loop would use recent frames to estimate which lanes are safe, trigger a lane change early enough, and check whether it succeeded. The model could review a collision between rounds and propose a larger clearance margin for the next attempt. This is where live feedback could improve reflex gameplay: fast feedback corrects movement, while slower feedback improves strategy. Only the local loop owns urgent inputs; an old model response must not overwrite a newer avoidance action. This is a proposed architecture, not a shipped controller.

For this take-home, keep selecting games the current controllers can play well. If reflex coverage becomes necessary, the smallest useful next experiment is one visually simple runner with a local hazard/lane controller. First use saved footage to check perception and estimate reaction windows; then compare against the existing timed baseline on a prespecified small set of fresh runs. Record every attempt, input timestamps and observation age, score/survival, missed hazards, and the fraction producing a visually verified highlight with an understandable action and payoff. Include frame-age-at-action median, tail and maximum delays with sample counts; a small trial is a feasibility check, not a reliability guarantee. Continue only if gameplay and usable-content yield improve. Keep native game time unchanged for this reflex test; evaluate any pause-assisted capture separately.
