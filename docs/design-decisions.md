# Design decisions and rationale

Updated 2026-10-07. This record preserves decisions, their reasons and superseded proposals. **D54 and the current [PLAN.md](../PLAN.md) take precedence:** the core branch discovers games, learns/plays/captures them, and edits shorts through a CLI; account creation and publication are manual. Earlier workbench/Instagram decisions describe the broader historical scope. The [acceptance record](acceptance.md) tracks current live results and remaining proof.

## Historical workbench constraints

Instagram's terms restrict automated account creation and automated access without its permission. The browser route is technically plausible and user-selected; it is not an officially supported provisioning API. Human code entry does not eliminate that platform restriction. Preserve this limitation in the handoff rather than claiming guaranteed unattended creation. [Instagram terms](https://help.instagram.com/581066165581870/)

These integration concerns belonged to the earlier workbench scope. They are not current core-pipeline blockers. Read the [acceptance record](acceptance.md) for current results; the [requirements audit](requirements-audit.md) preserves the earlier planning critique.

### Live-feedback boundary and options for reflex play

The shipped loop is **screenshot → model decision → native action batch → one-second settling delay → next screenshot**. It allows up to 175 seconds and ten decisions; the tenth, if reached, is evaluation-only. Each model call has a deadline of at most 30 seconds; a batch permits up to eight actions with a declared-duration budget of ten seconds. Browser/input overhead can make actual execution longer. The setup prompt assumes decisions may take 5–20 seconds, but that is an eligibility assumption, not a measured latency guarantee. These limits bound work; they do not ensure timely reactions. See [feedback](../src/server/games/feedback.ts), [runner](../src/server/games/runner.ts), and the [live experiments](acceptance.md#gameplay-improvement-experiments-2026-10-06).

The central problem is **observation age when input reaches the game**: capture/encoding, model transport/inference, and input scheduling all add delay. Later actions in a batch use an even older observation. The next opportunity to correct also waits for the batch and settling delay. A faster model or larger decision budget alone does not establish reflex capability. For illustration, a hazard requiring a response within 300ms cannot be handled by a decision arriving seconds later. The one-second settling delay fixed puzzle snapback; a reflex controller would need its own observation cadence rather than applying that delay to moving hazards.

The practical eligibility question is whether **observation age + time for the chosen input to take effect + uncertainty margin fits inside the remaining reaction window**. Also measure the gap between observations: a hazard can appear and become unavoidable while the controller is waiting. These are game-specific feasibility checks, not a new latency requirement from the brief. A deadline merely rejects a late call; it does not guarantee that an accepted decision is still relevant to the current scene.

Car Wash has a countdown and was correctly rejected by this feedback mode. Its successful plan was improved **between attempts**, then executed without model calls during urgent play. Sort It Out tolerates waiting and supports the screenshot loop. Both are useful results, with different control requirements.

| **Timed plans improved between attempts** | Predictable obstacle patterns, repeated routes, or timed sequences whose correct actions can be prepared in advance. The model reviews failures and adjusts timings for the next run. | Closest to the existing Car Wash experiment; no inference delay during execution. Random spawns and timing drift can invalidate a plan. Proven here for a timed wash, not unpredictable reflex play. |
| **Fast local controller with a slower model planner** | A simple runner or dodging game with visible lanes, hazards, and movement. Track positions and velocity from recent frames; local rules decide when to jump or change lane. The model interprets rules, chooses goals, and reviews failures between rounds or safe checkpoints. | Proposed first reflex experiment. Reuse existing vision libraries; [OpenCV optical flow](https://docs.opencv.org/4.13.0/d4/dee/tutorial_optical_flow.html) provides motion-tracking primitives, not a ready-made game player. Detection, prediction, and input timing still need game-specific validation. Keep urgent actions independent of model availability. |
| **Faster visual inference with short, interruptible actions** | Games whose reaction window exceeds measured end-to-end latency. A smaller/local model or a lower-latency remote model, cropped observations, and compact outputs could reduce delays. | Unmeasured here. Evaluate capture overhead and slow outliers as well as average inference time. An asynchronous design must use the latest frame, expire stale decisions, and avoid queued actions from obsolete states. Streaming text alone does not establish a usable action sooner. |
| **A policy trained from demonstrations, optionally refined with reinforcement learning** | Repeated use of one game or a stable family justifies learning a fast mapping from recent frames to controls. | Requires representative demonstrations with action timing, a reset/evaluation loop, and training resources; reinforcement learning also needs a useful reward. [VPT](https://arxiv.org/abs/2206.11795) demonstrates imitation learning and subsequent fine-tuning in Minecraft with a native 20Hz mouse/keyboard interface. This supports the approach's plausibility, not transfer to Astrocade. Defer for this take-home unless simpler control fails on a valuable game. |
| **Use a genuine in-game pause or safe checkpoint** | A game with verified pause controls or quiet intervals lets the model inspect the scene and choose the next route or short sequence. | Proposed fallback for obtaining footage, not proof of real-time reflex control. Verify that hazards actually stop during pause. Repeated pauses can interrupt the action; record them honestly and do not present edited footage as uninterrupted play. Do not replace the game's clock or assume browser timers stop every subsystem. |

These approaches can be combined: a model can select a tested skill while a local controller executes and corrects it. [Voyager](https://arxiv.org/abs/2305.16291) provides a precedent for model-guided reusable executable skills in Minecraft. Applying that separation to an Astrocade reflex controller is a design inference, not a result established by that paper or this project. Prefer a few bounded, tested controls over a general skill platform.

For example, in a lane runner the model could learn that coins increase score and barriers end the run, then choose a conservative coin route. A local loop would use recent frames to estimate which lanes are safe, trigger a lane change early enough, and check whether it succeeded. The model could review a collision between rounds and propose a larger clearance margin for the next attempt. This is where live feedback could improve reflex gameplay: fast feedback corrects movement, while slower feedback improves strategy. Only the local loop owns urgent inputs; an old model response must not overwrite a newer avoidance action. This is a proposed architecture, not a shipped controller.

For this take-home, keep selecting games the current controllers can play well. If reflex coverage becomes necessary, the smallest useful next experiment is one visually simple runner with a local hazard/lane controller. First use saved footage to check perception and estimate reaction windows; then compare against the existing timed baseline on a prespecified small set of fresh runs. Record every attempt, input timestamps and observation age, score/survival, missed hazards, and the fraction producing a visually verified highlight with an understandable action and payoff. Include frame-age-at-action median, tail and maximum delays with sample counts; a small trial is a feasibility check, not a reliability guarantee. Continue only if gameplay and usable-content yield improve. Keep native game time unchanged for this reflex test; evaluate any pause-assisted capture separately.
